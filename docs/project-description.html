01

The problem, framed honestly

Most public "retail AI" case studies quietly assume a data topology they don't have. Instacart's Market Basket dataset is a genuine gift for demand modeling — 3.42 million real orders, complete reorder history, basket composition down to cart position — but it describes one retailer's order history across users, not a multi-location inventory feed. There is no store dimension, no DC, no warehouse, and no observed stock level anywhere in it.

Rather than pretend that gap doesn't exist, ReorderIQ treats it as the interesting part of the problem. The demand layer — reorder prediction, basket association — is built directly on real transactions with zero simulation. The network layer — which store is which, how a DC pools risk across them — is constructed on top of that real signal, and its validity is tested statistically rather than assumed. Section 09 is a full ledger of which is which, because a system that hides that distinction is less trustworthy than one that states it up front.

Demand sensing: the reorder model

The task is scoped exactly the way the data supports it: for each user, using only their prior order history, predict which previously-purchased products reappear in their next order. Candidates are restricted to products a user has bought before — this is a reorder model by construction, not a first-purchase model, and that scoping decision is what keeps the labels honest.

Features (16, computed in DuckDB)

User-level (order cadence, basket size, historical reorder ratio), product-level (popularity, reorder rate, average cart position), and the interaction terms that carry the most signal — how many times this user has bought this product, how recently, and at what rate relative to their total order count.

Evaluation

Kaggle's actual competition metric is mean per-order F1: predict a set of products per order, score the set against the true set, average across orders. A single global probability threshold — tuned on a 90/10 user-level split so held-out orders are genuinely unseen — approximates the per-order-optimal thresholding winning solutions use.

05

Network construction & MEIO

Building the missing layer. 206,209 users are clustered on an 21-dimension department purchase-share profile plus shopping cadence (order frequency, basket size, order timing) into 18 synthetic stores via K-means. Candidate store counts (12, 15, 18, 20) were compared on silhouette score before settling on 18 — a mid-range count that balances network granularity against per-store sample size.

Silhouette scores for this kind of clustering land low by nature (0.05–0.08) — behavioral clustering on purchase shares doesn't form the tight geometric blobs spatial clustering does, so cluster quality is validated on a stronger test: 21 of 21 departments differ significantly across the 18 stores (Kruskal-Wallis, p<0.01), with a pseudo-F statistic of 9,397. The stores are behaviorally distinct nodes, not an arbitrary partition — a claim that's checked, not assumed.

Two-echelon MEIO

Store demand rolls up to a department-level "category DC" serving the whole network. Pooling demand variance at that upstream echelon is the textbook risk-pooling argument — aggregate demand across many stores is proportionally less variable than any single store's demand — quantified here rather than cited:

06

Basket intelligence

The one layer that is 100% real data end to end — no store simulation, no calendar reconstruction, nothing sampled for the primary output. Pairwise co-occurrence (support, confidence, lift) is computed via a SQL self-join across the full 33.8M-row order-product history — 415,479 candidate pairs among the top 2,000 products, scored exactly.

Two rule types come out of that scoring: high-lift pairs across any aisle read as complements ("frequently bought together" — Coconut Chocolate Bar → Chocolate Sea Salt, lift 329×). Same-aisle pairs with lift below 0.8 read as substitutes — shoppers pick one or the other rather than both (Bag of Organic Bananas ↔ Banana, lift 0.02×) — exactly the signal the control tower needs when a SKU is predicted to run short.

A genuine FP-Growth run (mlxtend) on a 106,310-order sample of the top 250 products surfaces multi-item itemsets pairwise analysis can't see — 1,475 frequent itemsets at 0.3% minimum support. Sampling here is a memory-tractability necessity (one-hot encoding 3.42M orders × 49,688 products isn't feasible); it is not used for the primary pairwise output.

07

The control tower

Deliberately not an LLM agent graph. Every decision here — is this an exception, which store covers the deficit, which SKU substitutes — is fully computable from the data. There's no ambiguous judgment call an LLM would improve, so the orchestrator is a plain, testable, dependency-free rule set.

The harder design problem was making "exception" mean something. A trailing moving-average forecast compared to the trailing average it was built from can't disagree with itself — that check flags nothing real. Instead, the control tower compares two independent estimates: the trained reorder model's demand signal (real behavioral features, forward-looking) against the historical baseline the safety stock was sized on — both expressed as each SKU's share of its store's total demand, which cancels the unit mismatch between "probability of the next order" and "units per week." Divergence beyond 1.5×/0.67× is the exception worth surfacing.

The first pass at this, using raw units instead of demand share, flagged 58.6% of positions — indistinguishable from noise. Re-deriving it against share of network demand brought that to a workable 4.9%, with a transfer donor or substitute attached wherever the network has one.

What's real vs. simulated

The ledger this whole project is built to justify. Read this before trusting any number above.

✓
Real
Every order, every reorder label
All 3.42M orders and 33.8M order-product rows are unmodified Instacart data. The reorder model and every association rule are trained/computed directly on it.
⚙
Simulated
The store network itself
Instacart has no store or DC dimension. The 18 "stores" are K-means clusters of users — a defensible, statistically validated proxy for store format, not real geography or operations.
⚙
Simulated
The calendar
Instacart gives only a gap (days_since_prior_order), not real dates. Weekly buckets are a cumulative sum per user starting at day 0 — relative spacing is real, cross-user calendar alignment is not.
⚙
Simulated
Lead times & service level
1-day store lead time, 3-day DC lead time, and a 95% target service level are stated modeling assumptions — no supplier or fulfillment data exists in this dataset.
⚙
Inferred
"Inventory" itself
There are no observed stock levels anywhere in this dataset. Every inventory figure here is a demand-coverage target computed from forecast + safety stock, not a shelf count.
✓
Checked
No leakage into the held-out order
Kaggle's test labels are withheld by design and unusable. All validation uses a 90/10 user-level split of the train set — the #1 way these projects silently break is candidate rows leaking the label they're predicting, and that was checked explicitly.
10

Limitations & what I'd change with more time

  • LightGBM was dropped for scikit-learn's HistGradientBoostingClassifier — this build environment has no Homebrew/libomp, and LightGBM's compiled extension won't load without it. Same family of algorithm; the F1 gap to the Kaggle benchmark is more plausibly explained by 16 features and zero tuning than by the swap itself.
  • Risk pooling assumes store-level demand independence within a department. Real regional demand correlates, which would shrink the 30.1% pooling benefit below what's shown here — a bound worth stating rather than hiding.
  • FP-Growth samples 106K of 3.42M orders and the top 250 of 49,688 products for memory tractability. The pairwise rules, which carry the primary substitution logic, do not sample.
  • Given another pass, the next investments would be per-order-optimal thresholding (closing the F1 gap to the Kaggle benchmark), a demand-correlation estimate to tighten the pooling bound, and a thin LangGraph layer over the existing rule functions purely for natural-language exception summaries — not for the decisions themselves.
