System architecture

Five layers, each feeding the next. LangGraph/LLM orchestration was deliberately skipped for the control tower — every decision below is computable from data, so a rule-based orchestrator is faster, cheaper, and fully testable.

1. Demand Sensing
Reorder-probability model per user × product, rolled up to store-level demand
→
2. Hierarchical Rollup
SKU → department-DC → store → network, bottom-up reconciled
→
3. MEIO
Two-echelon safety stock / reorder points, risk-pooled at the DC
→
4. Basket / Substitution
Exact pairwise + FP-Growth association rules
→
5. Control Tower
Exception detection + transfer & substitute recommendations

What's real vs. simulated

  • Real, unmodified: all 3.42M orders, 33.8M order-product rows, reorder labels, product/aisle/department taxonomy. The reorder model and association rules are trained/computed directly on this — no synthetic data anywhere in those two layers.
  • Simulated network topology: Instacart has no store or DC dimension. The 18 "stores" are K-means clusters of users on department purchase-share + cadence — a defensible proxy for store format/demographic mix, statistically validated (21/21 departments differ at p<0.01), but not real geography or real store operations.
  • Simulated calendar: Instacart gives only days_since_prior_order (a gap), not real dates. Weekly buckets are reconstructed via cumulative sum per user, starting each user at day 0 — relative spacing is real, absolute calendar alignment across users is not.
  • Simulated lead times & service level: 1-day store lead time, 3-day DC lead time, and a 95% target service level are modeling assumptions — Instacart provides no supplier or fulfillment lead-time data.
  • Inferred, not observed, inventory: there are no real stock levels anywhere in this dataset. "Inventory" here means demand-coverage targets (order-up-to levels) computed from forecasted demand and safety stock — not observed shelf or warehouse quantities.
  • Held-out test set unusable: Kaggle's eval_set='test' orders have labels withheld. All validation here uses a 90/10 user-level split of the train eval set, so held-out orders are genuinely unseen by the model.
